# MMWR Phase 2 — Core Data Model and Permission Contract

**Date:** 2026-09-28  
**Status:** Design contract for local schema work; identity, role, content, submission, reaction, profile-provisioning and application-email-verification migrations are authored. Identity/content received independent static review; the new email-verification migration has not yet been independently reviewed or executed on PostgreSQL. No accounts or real records have been created.
**Authority:** `HANDOFF.md`, `MASTER_PLAN.md`, and Phase 0 trust-boundary inventory.  
**Scope:** Identity, approved content, submission/moderation, evidence metadata, aliases/tags/locations, reactions, reports, revisions, audit events, and notifications. This document does not authorize a hosted Supabase project or production data.

## 1. Core boundaries

- Supabase Auth owns credentials, the private account email, and authentication factors. MMWR owns the separate `submission_email_verified_at` eligibility marker and its single-use email-verification token flow. Hosted/local Supabase Auth email confirmation must remain disabled so unverified users can sign in and read; app-level verification still gates every submission RPC. MMWR must not copy email or editable Auth `user_metadata` into a public profile or use it for authorization.
- `public` contains only deliberately exposed profile-self-service and sanitized, approved public preview data. Exposure requires explicit grants and RLS; a table being in `public` does not make it public-readable.
- `private` contains role assignments, full post text, submissions and their source text, evidence metadata and object paths, moderation material, reports, revisions, audit events, and notifications. It is not exposed through the Data API.
- A public preview is a separate data boundary from a full post body. For a currently published post, anonymous users may read only the approved title, primary name, public area, approximately five lines of public excerpt, and public evidence thumbnail. The thumbnail projection must not expose an object path or Storage key. Full-body and full evidence-file access require sign-in; email verification is not a reading or Reaction requirement. This follows the HANDOFF decision that signed-out readers see evidence thumbnails only while signed-in readers, including users with unverified email, may open/download eligible public evidence.
- Owner/Admin staff access requires both a matching database role in `private.user_roles` and a current `aal2` assurance claim. A role row alone is insufficient. High-risk approval and evidence-visibility changes remain Owner-only even at AAL2.
- Each mutable family has a server-owned lifecycle. A submitter cannot publish, hide, delete, or change a review decision by writing a status field. Every user-supplied value, role, identifier, and claim is untrusted until checked at the server/data boundary.
- Every app-owned table, including private-schema tables, must have RLS enabled. Grants and policies are designed together and scoped to the minimum operations needed. This document is a contract, not evidence that RLS has been implemented or verified.

Email stays in Auth and is not copied to profiles, post previews, reports, or analytics exports. The profile records only the app-owned submission eligibility timestamp. A DB trigger clears that marker and all outstanding tokens when the Auth email changes. Verification tokens are 256-bit random bearer values sent in a URL fragment, SHA-256 hashed before storage, valid for 30 minutes, one-use, and subject to a per-account limit of three requests per hour. Opening the link does not consume it; the user must confirm on the MMWR page. The email is sent only by a server-only SMTP module; no provider credentials are committed. Password reset uses Supabase Auth's PKCE callback with a fixed, allow-listed local destination. Authorization reads `private.user_roles`, never user-editable metadata or client-provided role claims.

### Explicitly separate future data domains

Analytics raw events/aggregates, campaign/customer/commercial records, and backup runs/manifests are not defined as core content records in this phase. Their future owners and access boundaries are already constrained: Analytics raw-event and IP retention must be separately decided; campaign/customer, quote, budget, and revenue data are Owner-only; backup metadata is restricted to operational staff and backup copies use the separate R2 policy. Their schemas and retention periods must be specified in their owning plans. The removed-content one-year period must not silently be reused for them.

**Suspension overlay:** A suspended user can still log in and read full published content. Suspension disables submission and Reaction while active. Permanent ban blocks login. By user policy, appeal, correction, and removal request channels remain closed pending policy confirmation; the UI must state that the channel is not yet available and must not expose a configured contact link. Expiration or removal of a temporary restriction is a server-owned, audited transition.

**Two-factor gate and recovery:** Supabase Auth owns TOTP factor enrollment/challenge, one-time recovery-code lifecycle, and the resulting assurance claim. Owner/Admin data access fails closed unless the database role, a current `aal2` session, and a signed `amr` TOTP method (`totp` or `mfa/totp`) are all confirmed; an AAL2 recovery-code session is restricted to factor replacement and cannot read staff data. Recovery-code generation is an opt-in Supabase Auth experimental API: the plaintext set is displayed once, Auth stores/manages it, a successful one-time code verification upgrades the session to AAL2, and repeated failures are locked by Auth. Client instances enable `auth.experimental.recoveryCodes`; each Auth environment must also enable recovery-code enrollment and verification with ten 16-character codes and a five-attempt/15-minute lockout. MMWR does not keep a duplicate recovery-code hash table. If recovery-code status/verification is unsupported or fails, the staff gate remains closed. After use, the page prompts the staff member to enroll a replacement TOTP factor, removes prior verified TOTP factors, and rotates the recovery set while a TOTP AAL2 session is active. This API is currently marked experimental by Supabase and must pass Staging checks before Production enablement.

**Security-event records:** MMWR's server-side security/audit event service may retain anomalous Owner/Admin sign-ins, repeated login or TOTP failures, factor/recovery/reset events, and relevant assurance/role-denial events for internal audit. By user policy, the only anomalous-login email source is the Owner/Admin recovery-code failure threshold; IP/device changes do not trigger mail, and device fingerprints are not collected. Other security events must not enqueue anomalous-login email. Supabase Auth provides authentication/factor state, recovery-code lifecycle, failed-code lockout, and assurance; the MMWR app owns the staff gate and application audit event recording/alert routing. Recovery-code alerting depends on the MFA Verification Hook, which current Supabase documentation lists for Teams and Enterprise and documents only `totp`/`phone` factor types; recovery-code hook delivery therefore remains unverified and must be proven on the exact Staging Auth version before the feature is considered usable. See [Supabase Auth Hooks](https://supabase.com/docs/guides/auth/auth-hooks) and [MFA Verification Hook](https://supabase.com/docs/guides/auth/auth-hooks/mfa-verification-hook). Event retention is governed by the unresolved Audit Log policy, not notification retention.

## 5. Project facts and intentionally deferred decisions

- This is a fresh, independent MMWR project. There are currently no real user/account records, submissions, posts, evidence files, reactions, audit events, or analytics records.
- There are no imported/licensed Malaysia region boundaries or real map locations. The current map is only an explicitly illustrative UI placeholder.
- The Our Little Age review is a selective feature/security inventory only. No user data, evidence, production database, credential, environment file, or application code is imported by this model.
- This file does not create schema, decide an unapproved retention duration, declare legal compliance, enable uploads, or connect a Supabase project.
- Open decisions before the associated feature becomes live include: Malaysia boundary source/licence; rejected-upload and active-evidence lifecycle; pending-submission/report retention; retention duration and legal holds for audit/Clarification records; exact TOTP recovery/reset operations supported by the selected Auth provider; audit retention and tamper-resistant storage; Reaction state after suspension/account deletion; legal holds and exceptions; and the operational implementation of deletion, backup expiry, and cache/index removal. Account-deletion identity handling is resolved by the Master Plan rule to unlink identity while retaining necessary audit: username-history rows are deleted under the user's explicit 2026-10-04 decision, while retained staff audit/Clarification records set actor references to NULL under forward migration `20261004200000_anonymize_retained_staff_audit_actors.sql`. The Hot-threshold and Reaction-icon settings audit tables reject mutation/truncation while allowing only Auth-driven actor nullification under `20261004210000_preserve_owner_audit_append_only.sql`; neither migration has been applied or verified.
- Malaysia counsel must review the content, privacy, correction, appeal, removal, and retention policies before public production use. Any policy change must be reflected in `HANDOFF.md` and this model contract before schema behavior is treated as settled.

## 6. Acceptance conditions for schema implementation

1. No public relation includes email, submitter identity, full private source text, evidence object paths, risk flags, reviewer notes, report details, audit records, or commercial data. Anonymous published-post projection is limited to title, primary name, area, approximately five lines of excerpt, approved public tags/time, and a thumbnail with no Storage path.
2. Public preview is limited to approved, currently published safe fields; hidden, draft, rejected, or removed records disappear from every public read path.
3. Full-body reads require authentication; publication/review status changes are server-owned; unverified accounts can read and React but cannot submit.
4. `private.user_roles` is not exposed to client roles. User metadata is never an authorization source. Staff authorization checks both database role and AAL2.
5. Owner-only decisions and Admin restrictions in the role matrix are enforced by grants/RLS/server authorization, not just UI.
6. Each table has RLS and explicit grants; each transition has an allow/deny verification. Any unresolved retention value remains explicitly unresolved until policy owners decide it.
7. No schema work based on this model introduces real data, external credentials, public boundaries, a remote project link, or Production migration.

These conditions describe the design target. Passing them requires the separate migration and local policy verification tasks; this document alone does not satisfy them.
