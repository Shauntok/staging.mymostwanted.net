# MMWR Phase 2 — Core Data Model and Permission Contract

**Date:** 2026-09-28  
**Status:** Design contract for local schema work; identity/role schema is authored and statically reviewed but not executed on PostgreSQL. No accounts or real records have been created.
**Authority:** `HANDOFF.md`, `MASTER_PLAN.md`, and Phase 0 trust-boundary inventory.  
**Scope:** Identity, approved content, submission/moderation, evidence metadata, aliases/tags/locations, reactions, reports, revisions, audit events, and notifications. This document does not authorize a hosted Supabase project or production data.

## 1. Core boundaries

- Supabase Auth owns credentials, email, email verification, and authentication factors. MMWR must not copy email or editable Auth `user_metadata` into a public profile or use it for authorization.
- `public` contains only deliberately exposed profile-self-service and sanitized, approved public preview data. Exposure requires explicit grants and RLS; a table being in `public` does not make it public-readable.
- `private` contains role assignments, full post text, submissions and their source text, evidence metadata and object paths, moderation material, reports, revisions, audit events, and notifications. It is not exposed through the Data API.
- A public preview is a separate data boundary from a full post body. For a currently published post, anonymous users may read only the approved title, primary name, public area, approximately five lines of public excerpt, and public evidence thumbnail. The thumbnail projection must not expose an object path or Storage key. Full-body and full evidence-file access require sign-in; email verification is not a reading or Reaction requirement. This follows the HANDOFF decision that signed-out readers see evidence thumbnails only while signed-in readers, including users with unverified email, may open/download eligible public evidence.
- Owner/Admin staff access requires both a matching database role in `private.user_roles` and a current `aal2` assurance claim. A role row alone is insufficient. High-risk approval and evidence-visibility changes remain Owner-only even at AAL2.
- Each mutable family has a server-owned lifecycle. A submitter cannot publish, hide, delete, or change a review decision by writing a status field. Every user-supplied value, role, identifier, and claim is untrusted until checked at the server/data boundary.
- Every app-owned table, including private-schema tables, must have RLS enabled. Grants and policies are designed together and scoped to the minimum operations needed. This document is a contract, not evidence that RLS has been implemented or verified.

### Explicitly separate future data domains

Analytics raw events/aggregates, campaign/customer/commercial records, and backup runs/manifests are not defined as core content records in this phase. Their future owners and access boundaries are already constrained: Analytics raw-event and IP retention must be separately decided; campaign/customer, quote, budget, and revenue data are Owner-only; backup metadata is restricted to operational staff and backup copies use the separate R2 policy. Their schemas and retention periods must be specified in their owning plans. The removed-content one-year period must not silently be reused for them.

**Suspension overlay:** A suspended user can still log in and read full published content. Suspension disables submission and Reaction while active. Permanent ban blocks login and exposes the approved human appeal path. Expiration or removal of a temporary restriction is a server-owned, audited transition.

**Two-factor gate and recovery:** Supabase Auth owns TOTP factor enrollment/challenge and the resulting assurance claim. MMWR's server-side route/data authorization must fail closed: if role lookup, assurance lookup, or authentication-provider verification fails, or a current `aal2` claim is absent, staff access is denied. An AAL2 session does not grant broader data scope than the role matrix. Owner/Admin TOTP is mandatory before formal management access. MMWR must generate one-time recovery codes, show them once at generation, and store only secure hashes server-side; the app must not later reveal plaintext codes. Redemption must atomically verify and consume/delete (or mark used) the matching stored hash so that concurrent attempts and replays fail. Recovery and factor-reset actions require separately designed, audited secure flows. Exact provider capabilities and reset procedures remain to be verified during the authentication implementation.

**Security-event records:** MMWR's server-side security/audit event service records anomalous Owner/Admin sign-ins, repeated login or TOTP failures, factor/recovery/reset events, and relevant assurance/role-denial events. Supabase Auth provides authentication/factor state and assurance; the MMWR app owns the staff gate, recovery-code lifecycle, and application audit event recording/alert routing. Critical security events may alert Owner by email under the approved exception; event retention is governed by the unresolved Audit Log policy, not notification retention.

## 5. Project facts and intentionally deferred decisions

- This is a fresh, independent MMWR project. There are currently no real user/account records, submissions, posts, evidence files, reactions, audit events, or analytics records.
- There are no imported/licensed Malaysia region boundaries or real map locations. The current map is only an explicitly illustrative UI placeholder.
- The Our Little Age review is a selective feature/security inventory only. No user data, evidence, production database, credential, environment file, or application code is imported by this model.
- This file does not create schema, decide an unapproved retention duration, declare legal compliance, enable uploads, or connect a Supabase project.
- Open decisions before the associated feature becomes live include: Malaysia boundary source/licence; rejected-upload and active-evidence lifecycle; pending-submission/report retention; username-history duration, former-username reuse and post-deletion handling; exact TOTP recovery/reset operations supported by the selected Auth provider; audit retention and tamper-resistant storage; Reaction state after suspension/account deletion; legal holds and exceptions; and the operational implementation of deletion, backup expiry, and cache/index removal.
- Malaysia counsel must review the content, privacy, correction, appeal, removal, and retention policies before public production use. Any policy change must be reflected in `HANDOFF.md` and this model contract before schema behavior is treated as settled.

## 6. Acceptance conditions for schema implementation

1. No public relation includes email, submitter identity, full private source text, evidence object paths, risk flags, reviewer notes, report details, audit records, or commercial data. Anonymous published-post projection is limited to title, primary name, area, approximately five lines of excerpt, approved public tags/time, and a thumbnail with no Storage path.
2. Public preview is limited to approved, currently published safe fields; hidden, draft, rejected, or removed records disappear from every public read path.
3. Full-body reads require authentication; publication/review status changes are server-owned; unverified accounts can read and React but cannot submit.
4. `private.user_roles` is not exposed to client roles. User metadata is never an authorization source. Staff authorization checks both database role and AAL2.
5. Owner-only decisions and Admin restrictions in the role matrix are enforced by grants/RLS/server authorization, not just UI.
6. Each table has RLS and explicit grants; each transition has an allow/deny verification. Any unresolved retention value remains explicitly unresolved until policy owners decide it.
7. No schema work based on this model introduces real data, external credentials, public boundaries, a remote project link, or Production migration.

These conditions describe the design target. Passing them requires the separate migration and local policy verification tasks; this document alone does not satisfy them.
