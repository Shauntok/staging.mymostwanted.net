# MMWR Phase 7 — Backup and Recovery Design

**Status:** Local-only implementation and isolated restore verification. A full synthetic encrypted database-plus-Storage backup was restored from one run into a disposable Supabase stack, with database readback, Auth/Storage startup, and object path/byte verification. This does not prove full Storage metadata fidelity: Storage API re-upload regenerates object ownership and timestamps. The current Supabase Storage restore adapter is loopback-only; hosted and custom remote URLs are rejected before client creation. No real R2 run, schedule, or hosted environment has been configured. All backup and restore runtime gates remain OFF.

## Approved direction

- Back up the Supabase Postgres database and all MMWR Storage objects to a separate Cloudflare R2 bucket.
- Keep the retention target at 7 daily, 4 weekly, and 6 monthly restore points.
- Keep credentials server-side and encrypt backup payloads before they leave the worker.
- Support scheduled runs and an Owner-initiated run, with run status and audit history visible only to authorized operations staff.
- A restore must target an isolated environment. Production restore is never an automatic action.
- RPO/RTO are explicitly TBD until the Owner chooses values. Database and Storage backup retention must not inherit the one-year removed-content policy.

## Proposed implementation boundary

Use a dedicated Node backup worker, separate from Next.js request handlers and the evidence-scanner worker. A web request may enqueue an Owner-authorized backup job, but must not perform a database dump or stream evidence objects itself. The worker owns database export, private Storage enumeration/download, encryption, R2 upload, integrity verification, retention planning, and job completion reporting.

Use the Supabase CLI `db dump` workflow for database exports rather than an unfiltered `pg_dump`. The export set must include role definitions, schema, table data, and the `supabase_migrations` history needed to resume migrations. The worker image/runtime must include the CLI's supported Docker-compatible runtime and a Postgres dump image compatible with the source database major version. It must not mount a general-purpose Docker socket into an internet-facing application container. The eventual worker host/runtime is an environment decision for Phase 8; this document does not select or provision one.

Enumerate every bucket and object through authenticated server-side Storage APIs. Fail the run if an object disappears, cannot be read, or changes incompatibly while being copied; do not silently create a partial backup. Store the original bucket/object mapping only inside an encrypted manifest. Use opaque object names in R2 and keep source paths, filenames, account identifiers, and submitted content out of logs and unencrypted metadata.

Encrypt each export/object and the manifest with authenticated encryption using a dedicated backup key held only in the environment's secret manager. Use unique nonces, verify authentication tags and plaintext hashes during restore, and persist a manifest containing format version, run ID, UTC timestamps, object counts, byte counts, and SHA-256 checksums. The manifest must not expose source names or paths. Do not reuse the analytics HMAC key or the Owner IP-block HMAC key for encryption.

## Retention and deletion guard

Retention selection is computed by calendar bucket: keep the newest seven daily points, four weekly points, and six monthly points. A point that is selected by more than one tier is stored once. Before any deletion code is enabled, verify the candidates and their integrity, and confirm the target bucket's protection policy. Automatic pruning stays disabled until the Owner chooses the R2 immutability/object-lock policy and Staging proves that expiration cannot remove the only valid restore point. R2 bucket-lock rules can override lifecycle deletion, so the two policies must be configured and verified together.

`backup/retention.mjs` currently implements only a dry-run selector. It requires an explicit IANA time zone, selects only successful integrity-verified full backups, returns the union of the daily/weekly/monthly keep sets, and identifies older verified restore points as deletion candidates. It performs no deletion and excludes incomplete or unverified runs from deletion eligibility.

`backup/r2.mjs` currently provides an OFF-by-default S3-compatible Cloudflare R2 adapter. It derives the HTTPS endpoint from a validated account ID, accepts credentials only from the environment, uses opaque run/artifact object keys, and exposes encrypted-object upload/head/read/list operations. It deliberately has no delete operation. A successful SDK upload is not yet treated as backup verification; the future Worker must download and verify the object bytes against the locally computed encrypted digest before marking a run complete.

`backup/worker.mjs` provides the environment-agnostic full-run orchestrator. It accepts injected database-export and Storage source adapters, plus an encrypted object-store adapter. A run is OFF unless `MMWR_BACKUP_ENABLED` is exactly `true`; it creates a private temporary directory and currently requires eight database components: roles, default schema/data, Auth schema/data, Storage schema/data, and migration history. The CLI exporter requests Auth and Storage schema/data explicitly. Supabase CLI 2.118.0 still filters `auth.schema_migrations` and `storage.migrations` from data-only output, so the exporter now runs two additional plain-format `pg_dump` commands restricted to exactly those tables, then combines each result with the matching CLI data artifact. The password goes only in the child environment as `PGPASSWORD`; the database URL has no embedded password. The local Postgres 17.6 dump emitted both required `COPY` statements and all 82 Auth / 73 Storage migration rows. Unit tests check the exact table allowlist, eight artifact kinds, and credential handling. The worker runtime must provide a `pg_dump` client compatible with the source server major version via `PG_DUMP_PATH` or `PATH`. This closes the observed local data omission, but merged dump SQL and supported restore ordering still require an isolated restore drill. The worker captures and paginates the Storage inventory, checks each source object after download, then re-reads the complete inventory and fails if bucket/object names, size, MIME/cache metadata, or modification times changed during the copy. It encrypts and uploads each artifact, downloads it and verifies encrypted hash, GCM tag, plaintext hash, and size, then writes and verifies the encrypted manifest. The manifest records the database export window and declares the export model as independent snapshots. A successful status proves cryptographic artifact integrity and unchanged Storage inventory during copying; it does **not** prove a transactionally consistent point-in-time snapshot across database and Storage, nor that Storage objects and database references were observed atomically. The workflow makes separate reads for roles, default schema/data, Auth schema/data, Storage schema/data, the two targeted migration tables, and migration history. Do not treat `integrityVerified` as evidence of point-in-time consistency or proven restorability. Failure status is a fixed code and does not include provider exception text. Temporary plaintext and ciphertext files are removed when the run ends. The durable run ledger and failure-email producer are local; scheduler, Owner trigger, email delivery configuration, and recovery executor are not connected or verified. Failed runs can leave opaque, unreferenced R2 objects; automated orphan cleanup is intentionally absent until lifecycle/deletion policy is chosen.

`backup/supabase-cli-export.mjs` requests roles, default-filtered schema/data, explicit Auth schema/data, explicit Storage schema/data, and migration-history artifacts. It does not run an unfiltered `pg_dump`; the only direct `pg_dump` table includes are the exact pair `auth.schema_migrations` and `storage.migrations`. CLI output inspection found 27 Auth / 10 Storage table definitions and 26 / 9 data COPY statements; the two missing migration ledgers were verified locally at 82 / 73 rows and added by the filtered exports. Auth troubleshooting guidance warns missing `auth.schema_migrations` state can trigger migration retries: https://supabase.com/docs/guides/troubleshooting/an-invalid-response-was-received-from-the-upstream-server-error-when-querying-auth-RI4Vl-. Merged dump SQL and supported restore ordering remain unverified until an isolated restore drill. Platform “Restore to a new project” does not copy Storage objects or bucket settings. Project-specific Auth/Storage customizations, provider settings, secrets, extensions, Storage bucket configuration and binary objects each require explicit restore planning. The exporter passes a passwordless `SUPABASE_DB_URL` as an argument and supplies `SUPABASE_DB_PASSWORD` only in a restricted child-process environment; the direct table dumps receive that password as `PGPASSWORD` in the same restricted environment. The password is never included in argv, inherited R2/encryption credentials are excluded, and CLI stdout/stderr are discarded. The migration-history artifact combines separate schema and data dumps. These separate commands produce independently observed database snapshots; no shared snapshot or cross-resource quiescence is currently established. The worker image must pin a CLI version and provide a `pg_dump` client compatible with the selected source major version.

`backup/supabase-storage-source.mjs` now provides a server-only Supabase Storage adapter using a secret key supplied at runtime. It walks every bucket and nested folder in pages, keeps pagination state in opaque in-memory cursors, downloads through short-lived signed URLs pinned to the configured Supabase origin, and compares listed size/modified time with Storage `info` after the download. The encrypted manifest stores bucket ID/name, public flag, file size limit, and allowed MIME types. The orchestrator now re-lists buckets and objects after copying to detect changes during the Storage copy window. This narrows but does not eliminate races between paginated listings, and it does not align the Storage inventory with the database exports' independent snapshot times. Lifecycle configuration and custom Auth/Storage schema policies still require explicit restore steps. It does not log bucket paths or signed URLs. `createSupabaseStorageSource()` combines this Storage adapter with the database CLI exporter and satisfies the orchestrator source interface. Source-adapter behavior remains untested until the later local verification window.

`backup/run-scheduled.mjs` composes the source adapter, R2 adapter, encrypted worker, and service-only status writer for a single scheduled run. `npm run backup:once` is an OFF-by-default one-shot command for a future isolated worker host; it does not install a schedule, expose a web endpoint, or enable the web process. The database major version is an explicit environment value that must be confirmed from the selected source project before use. This entrypoint has not been run.

The scheduled entrypoint now creates its status writer before constructing R2 and database/Storage source adapters. `runFullBackup()` writes the initial `running` ledger row before checking worker-only configuration or preparing those adapters, so missing R2/database-export/encryption settings and local workspace/byte-budget setup errors can transition that run to a fixed `backup_failed` status without starting an export. If the Supabase URL/service credential is missing or the status RPC/database itself is unreachable, no durable ledger write is possible; the process fails with a generic CLI message and does not prepare sources or upload artifacts. This boundary must be verified in Staging, including the no-export/no-upload properties.

`backup/restore-plan.mjs` validates an already decrypted manifest and builds a read-only checklist for a specifically named isolated target. It refuses source/target equality and any environment label other than `isolated`, and requires explicit Auth/Storage schema and data artifacts. It does not download, decrypt, connect to Supabase, invoke `psql`, or write data.

`backup/restore-storage-run.mjs` connects a successful, integrity-verified run summary and injected encrypted object store to the Storage restore flow. It validates the run and target identity before remote reads, verifies the manifest object's stored encrypted hash/size and AES-GCM tag, parses the authenticated manifest, then downloads and decrypts every Storage object to a private temporary workspace. Each object must match both the R2 metadata and manifest encrypted digest/size; plaintext must match the manifest digest/size. Only once all Storage artifacts are decrypted does it invoke `backup/restore-storage.mjs`, which rechecks files, requires an explicitly isolated target with source/target/adapter project refs bound, rejects unknown or conflicting buckets and non-empty target buckets, creates missing bucket configurations, uploads with overwrite disabled, and reads each object back to compare exact size and SHA-256. `backup/supabase-storage-target.mjs` implements the privileged Storage adapter with recursive/paginated inventory, private service-key closure, HTTPS/local-loopback URL restrictions, bounded object upload, and bucket policy mapping. The workflow never restores the database and never deletes target state; a mid-run failure reports that the target may be partial. It has synthetic encrypted-artifact tests, but no successful restore into a separate empty Supabase project or coordinated database restore, and no R2 credentials/run were used. Therefore this does not establish full backup restorability, point-in-time consistency, or RPO/RTO; backup/restore activation remains OFF.

`backup/restore-database-run.mjs` authenticates a successful run manifest, checks a target adapter's read-only preflight identity (`projectRef`, `isolated`, `pristine`), then downloads and AES-GCM/hash/size verifies every required database component into a private temporary workspace before its first write. It applies the eight SQL artifacts in restore dependency order through `targetDatabase.applyArtifact`. `backup/supabase-psql-target.mjs` implements a host loopback target with credentials passed only through the child environment and a Docker-local target bound to the exact `supabase_db_<project_id>` container. The Docker target streams SQL through stdin and uses the local `supabase_admin` database role; both variants suppress SQL diagnostics. A read-only preflight rejects application tables before the target is treated as pristine. Data artifacts use one transaction and set `session_replication_role=replica` for the psql session. A failed apply stops immediately, does not retry or auto-clean target data, and reports the target may be partial and must be discarded. The Docker adapter has passed a synthetic encrypted eight-component restore into a fresh disposable Supabase Postgres stack; it has not yet been run against the actual MMWR export set, so managed-role/schema compatibility remains open. `MMWR_BACKUP_RESTORE_ENABLED` is a dedicated false-by-default gate. Synthetic tests verify zero writes for invalid/non-pristine inputs and damaged components, all-artifact verification before writes, loopback/container binding, dependency ordering, password handling and stop-on-first-apply-failure. Do not enable this gate in a deployed environment. The Storage runner remains separate, so a single encrypted DB+Storage recovery has not been proven.

**Storage object metadata limitation:** The Storage database dump deliberately excludes `storage.objects`; restoration uploads bytes through the supported Storage API. A read-only query of the isolated restore confirmed the restored object has `owner_id IS NULL`; Storage API upload also assigns a new modification timestamp. MIME type and cache-control metadata, bucket policy, path, and bytes are preserved by the current flow, but the source owner ID and original modification timestamp are not. This matters because MMWR's account-deletion and derivative-cleanup safeguards inspect `storage.objects.owner_id` and object paths, while `private.evidence_metadata.uploaded_by` supplies an additional evidence association. Real recovery acceptance must prove every evidence/thumbnail reference is still protected and accessible under the restored identities, and must resolve whether owner/timestamp fidelity is required before any restore is treated as production-recoverable. Do not write directly to Storage-managed tables as a workaround without a supported, version-verified method. Phase 7 remains incomplete and all runtime gates remain OFF.

**2026-10-05 supported-path feasibility check:** Current Supabase guidance confirms that Storage object ownership is derived from the JWT `sub`, and writes made with the service key do not assign an owner. The Storage schema guidance says to treat Storage metadata rows as read-only and perform object operations through the Storage API. The installed Storage SDK's `FileObject` contract also marks owner data as not returned by `list()`; listing does expose creation/update timestamps, but the supported upload flow assigns new timestamps. This confirms the current API restore cannot faithfully recreate the original `owner_id` or timestamps. No direct SQL mutation, user impersonation, or alternate Storage write path was introduced. Continue to keep restore acceptance open until Supabase documents a supported metadata-preserving operation or the Owner explicitly accepts the resulting recovery semantics after reviewing all MMWR access, deletion, and audit effects. - Require an explicit restore job and a separately configured isolated target; never infer the target from the source URL.
- Reject source and target project references that are equal. Reject Production targets unless the Owner separately authorizes a Production recovery operation after the isolated restore has passed review.
- Verify the encrypted manifest, every authentication tag, every checksum, required dump components, and Storage object count before applying any database or object writes.

## Not implemented / confirmation gates

- Dedicated worker runtime and scheduler; R2 account, bucket, region/location, and credentials.
- Backup encryption-key storage/rotation and recovery access procedure.
- Retention-pruning and R2 object-lock/immutability policy.
- Database dump/restore format and compatibility against the actual Supabase database major version.
- Cross-version restore compatibility and application-level recovery authorization. The managed migration-ledger export and custom-schema restore path have passed only against the current pinned local Supabase/PostgreSQL stack; Staging and other versions remain unverified.
- Owner decision on the managed-database recovery source and cost: Supabase's platform restore-to-new-project flow includes database/Auth data from a physical backup but requires physical backups and is documented as a paid-plan feature; it does not copy Storage objects or bucket settings. This is a possible recovery path, not an R2 export and not yet selected.
- A shared point-in-time database snapshot and atomic consistency boundary with Storage; the current implementation is best-effort and must not claim atomic consistency.
- Storage bucket policy/configuration, custom Auth/Storage schema changes, provider settings and restore ordering against the real MMWR schema.
- Exact Storage object metadata recovery. The current Storage API upload regenerates timestamps and the local service-key restore produced null `owner_id`; verify a safe policy for evidence and derivative ownership before production recovery.
- RPO/RTO targets, alert recipient/delivery policy, and Staging recovery evidence.

All runtime flags must remain OFF until the worker, key custody, R2 permissions, backup/restore validation, retention behavior, and notification path have passed the later local test and Staging acceptance gates. This plan does not authorize connecting to any real Supabase, Cloudflare, Staging, or Production service.

### 2026-10-04 local worker hardening

`backup/worker.mjs` now bounds each Storage object to the configured `MMWR_BACKUP_MAX_STORAGE_OBJECT_BYTES` cap (10 MiB sample default; supported override up to 1 GiB), rejects inventory sizes above the cap before download, and meters actual streamed bytes against both the cap and listed object size. A short stream or a chunk that exceeds either bound fails before that chunk is written. The Supabase adapter also rejects/cancels an oversized, malformed, or inventory-mismatched `Content-Length` before returning the stream; the worker-side meter remains authoritative when the header is absent or misleading. An explicit `MMWR_BACKUP_MAX_TOTAL_STORAGE_BYTES` budget now bounds the initial and final inventory's combined source bytes; it is required before a run can proceed. These source-byte caps are not exact temporary-workspace caps: encryption/readback require several copies and database exports are separate, so the isolated worker still needs capacity planning.

Each remote artifact verification now gets unique private temporary filenames. This fixes the manifest path collision: `saveEncryptedArtifact()` verifies the uploaded manifest once, then the run verifies it a second time before parsing; those readbacks no longer both target the same `wx` paths. Staging acceptance now requires this repeated manifest check plus cleanup/overflow cases. No worker, database, test, build, R2, or hosted environment was run; backup remains OFF and cannot yet claim complete Supabase Auth/Storage database coverage.

**2026-10-06 restore-gate parity:** The Storage restore coordinator now enforces the same default-off `MMWR_BACKUP_RESTORE_ENABLED` gate as the database restore coordinator, before any backup-object read or target inventory call. A regression proves the closed gate performs zero source and target calls. Synthetic tests pass; the gate remains off and no hosted project/R2 is touched.
The opt-in local Storage restore test sets the restore gate only around its synthetic restore call and restores the prior environment value in `finally`; it remains skipped unless `MMWR_TEST_LOCAL_STORAGE_RESTORE=true` is explicitly set.
