## Goal and boundary

List cards may show an image only when an Owner has allowed that evidence to be used as a public thumbnail, the file has passed malware scanning and image decoding, and its post is currently published in the public projection. A thumbnail is a derivative, never the original evidence object. Internal evidence must never be reachable through this path.

## Proposed flow

1. Keep uploads in the existing private quarantine bucket. Do not create public Storage URLs or expose original object paths.
2. After the existing scanner verifies an image signature and ClamAV reports it clean, create a bounded raster derivative in the scanner process. Accept only JPEG, PNG, and WebP; reject SVG, animated or unsupported formats, oversized dimensions/pixel counts, and decode errors. Auto-orient, resize to the card limit, re-encode to WebP, and strip metadata. Never log image bytes, contents, or paths.
3. Produce a derivative only for evidence whose Owner-controlled visibility is `public_thumbnail`. Upload it to a dedicated **private** derivative bucket. Bind the derivative to the scan job lease and evidence ID; do not trust a client-provided path or a scan result alone. Keep the derivative object key private.
4. Add a server-only public thumbnail route keyed by published post and bounded image slot. On every request, query current publication and evidence-visibility state before reading the private derivative. Return only the derivative bytes with a fixed image content type, bounded response size, `X-Content-Type-Options: nosniff`, and conservative no-store caching until hide/withdraw invalidation behavior is proven. Return a neutral not-found response for every ineligible state.
5. Public list RPCs may expose availability only when a usable derivative exists. They must never return raw evidence URLs, bucket names, signed URLs, object keys, private evidence IDs, or scan details. Lists request the derivative route only for eligible public posts.

## Required lifecycle integration

- Owner switching visibility to `internal_only`, a post being hidden/removed, evidence deletion, and account-deletion processing must prevent further delivery and remove or safely retain the derivative according to the approved evidence-retention policy.
- Backup enumeration, completeness manifests, and isolated restore must include the derivative bucket. Restore validation must confirm derivative/evidence links without turning the private bucket public.
- Add explicit storage budget, derivative maximum dimensions/bytes, rate limits, orphan cleanup, and failure behavior. A derivative failure must not change the evidence scan result or block a post; the card uses its normal no-image state.
- Keep worker and route defaults OFF. Do not generate derivatives for the current local data or enable upload/scan/publication as part of implementation.

## Acceptance checks before this Phase 4 item can be marked complete

- Synthetic integration fixtures prove delivery succeeds only for clean, Owner-approved evidence attached to a currently published post.
- Requests for pending, rejected, infected, internal-only, unpublished, hidden, removed, unknown, or revoked evidence return no image; state changes take effect on the next request.
- Public RPC/API responses contain no source URL, signed token, bucket, object key, or private evidence metadata. The derivative bucket rejects anonymous direct access.
- Raster limits, malformed/decompression-bomb files, metadata stripping, output MIME/signature, lease replay, upload failure, and orphan cleanup are tested.
- Account deletion and backup/restore tests include derivatives and prove that no source evidence becomes public.
- Existing submission and scanning switches remain OFF; no hosted project, bucket, billing feature, or deployment is changed during local implementation.

## Supabase image transformation assessment

Supabase documents support image transformations on private-bucket signed URLs, but those URLs are bearer links valid until expiry and transformations can incur managed usage costs. They expose a Storage URL/token to the recipient and do not create the persistent, lifecycle-managed derivative required here. Therefore, do not use transformed signed URLs as the anonymous list-thumbnail mechanism. If revisited, require an explicit cost review and a revocation assessment first.
