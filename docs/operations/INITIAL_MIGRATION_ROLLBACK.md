# Early-phase migration rollback and recovery guide

This guide records recovery strategies for the 22 early migrations that are not covered by the later Phase 3, Phase 5, or Phase 7 rollback guides. The set spans Phase 2 identity/Auth work, Phase 4 public browsing and reading, and the first Phase 5 Page View aggregation migration. It is a review aid, not executable down SQL, and does not authorize changes to a database.

## Rules before recovery

1. Confirm the exact target environment and compare its migration ledger with the full applied sequence. A local ledger or this document cannot establish hosted state.
2. Take and verify an environment-specific backup before any schema change. If a backup cannot be verified, keep the feature disabled and use a forward correction.
3. Disable the relevant application and database gates and stop dependent workers before recovery. Do not weaken RLS, function ACLs, email verification, or the authenticated reading boundary to restore an older application build.
4. Prefer a reviewed forward migration. Never edit or delete an applied migration, reverse one migration in isolation, or restore an old function body without checking every later replacement.
5. Preserve role-change, reaction, analytics, and settings audit records; preserve verified-email state and public/private records. A rollback must not silently alter user state or erase retention evidence.
6. Any destructive rehearsal belongs only in isolated Staging with synthetic data. Record the ledger, backup evidence, commands, and before/after checks; never use Production as the rehearsal target.

## Inventory boundary

The current worktree contains 103 migration files. This guide covers 22 early migrations, including the empty no-op artifact listed above; later date bands are tracked in the Phase 3, Phase 4, Phase 5, Phase 6, and Phase 7 rollback guides. The migration-name audit found an exact filename entry for every migration across those guides. This is documentation coverage only: it is not a rollback rehearsal, dependency proof, or evidence that a target database is restorable. Check the inventory against the current migration files and target ledger after any new migration is added. No rollback is recorded or authorized by this document.
