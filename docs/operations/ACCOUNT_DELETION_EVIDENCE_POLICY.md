# Account deletion and evidence review policy

Status: product handling rule confirmed by the user on 2026-10-04. The migration chain and synthetic pgTAP fixtures have been exercised in the disposable local Supabase database. The Node Worker has also been tested against synthetic localhost services using the installed SDK; it has not deleted a real Auth identity or accessed hosted services. Every request/cleanup gate remains OFF outside rolled-back test fixtures.

## Confirmed handling

- An enabled request changes an eligible ordinary account to `deletion_pending`; the user can cancel for seven days. Staff accounts cannot request this flow.
- After the seven-day period, automatic cleanup may delete only an account with no evidence Storage objects and no evidence metadata owned by that account.
- If any evidence object or metadata remains, the worker changes the account to `deletion_review_required`, keeps account restrictions in place, and leaves every file and metadata row untouched. An Owner-only, recent-TOTP queue displays the username, request time, and review reason using stable 50-row keyset pages; it exposes neither profile IDs nor controls to resolve cases. Deletion, transfer, or retention decisions still require a separately confirmed policy and an audited Owner action.
- An Auth deletion error response or a thrown transport failure also moves the account to `deletion_review_required`; the worker does not loop retries automatically. Before calling Auth, it writes a service-only attempt checkpoint. If the worker stops after that checkpoint and cannot record a definite result, an expired claim moves to review with `auth_cleanup_uncertain` instead of retrying. A transport timeout can leave the provider-side outcome uncertain, so Staging must separately exercise definitely-not-delivered and ambiguous outcomes.
- The application gate `ACCOUNT_DELETION_CLEANUP_ENABLED` and database gate `account_deletion_cleanup` both default to `false`. The existing request gate `ACCOUNT_DELETION_ENABLED` and database flag `account_deletion` also remain independently default-off. The worker requires all applicable gates.
- No scheduled job is configured. The worker is only a bounded one-shot entry point for a separately authorized future environment.
- Turning a gate OFF does not cancel an Auth HTTP request that already passed the durable attempt checkpoint. Stop the Worker before emergency maintenance; a marked claim that cannot be reconciled becomes Owner review after lease expiry.

## Relevant data relationship

`private.evidence_metadata.uploaded_by` uses `ON DELETE SET NULL`, while evidence rows are linked to a submission or post. The private Storage bucket is `mmwr-evidence-quarantine`; upload paths begin with the uploader's Auth user ID. Before deleting an Auth account, the database checks the Storage owner ID, the upload path prefix, and the evidence metadata owner field. The worker does not list file names, delete objects, or transfer ownership. This fail-closed check also catches orphaned metadata and unregistered objects under the uploader prefix.

## Username history on account deletion

The user confirmed that account deletion removes that account's historical username rows. Forward migration `20261004190000_mmwr_delete_username_history_on_account_deletion.sql` changes `private.username_history.user_id` from `ON DELETE RESTRICT` to `ON DELETE CASCADE`; deleting the Auth identity therefore removes the current Profile and username-history rows, while unrelated audit records use their separately defined retention behavior. Historical names are not retained or reserved and may be reused subject to the current-profile uniqueness constraint. The identity pgTAP case verifies this cascade in the local test database only; hosted acceptance remains open.

## Retained staff records on account deletion

The Master Plan requires account deletion to unlink identity while preserving necessary audit. Accordingly, forward migration `20261004200000_anonymize_retained_staff_audit_actors.sql` changes the five restrictive Auth references to `ON DELETE SET NULL`: `analytics_valid_read_settings_audit.actor_user_id`, `post_reaction_icon_audit.actor_user_id`, `post_relationships.created_by`, and `clarification_removal_proposals.proposed_by` / `decided_by`. It makes required actor columns nullable, preserves all audit/relationship/proposal fields, and permits a decided proposal to retain its decision, reason and time when its decision-maker is removed. The Clarification relationship guards allow only the narrow actor-nullification update while continuing to reject other unauthenticated relationship changes. Follow-up migration `20261004210000_preserve_owner_audit_append_only.sql` also makes the two retained Owner settings audit tables append-only, with the exact actor-nullification as their sole update exception. No records cascade-delete under these migrations. They are applied and covered by synthetic tests locally; each retained table, constraint and mutation guard still requires isolated Staging acceptance before hosted cleanup can be enabled.

## Local implementation boundary

`account-deletion:once` requires the application cleanup gate plus the server-side Supabase secret. Its database claim RPC additionally requires both database flags, only claims expired non-staff accounts, checks for evidence before returning an account ID, and uses a 30-minute claim lease for interrupted runs. The claim migration samples eligibility and lease timestamps after locking each profile so lock waits do not consume the new lease. Before Auth deletion, the Worker must successfully write a service-only attempt checkpoint, which repeats the gate/lease/evidence checks. Each Supabase request has a 20-second client timeout. Only an explicit provider 4xx refusal moves the account to Owner review as `auth_cleanup_failed`; SDK-returned transport errors, infrastructure errors, failed response decoding, and thrown exceptions/timeouts move it to `auth_cleanup_uncertain`, because the provider may have completed the request before the response was lost. Neither outcome is retried automatically, provided the review RPC can be reached. If the worker stops after the checkpoint, an expired claim also becomes `auth_cleanup_uncertain` review and will not call Auth again. Database reconciliation is required before any later operation. Console output contains aggregate counts and fixed failure text, not account IDs, file paths, credentials, or provider errors. The `claim records returned` count includes only IDs returned to the Worker; accounts moved to review inside the database claim RPC are not included in that count. `authOutcomesSentForReview` counts Auth outcomes sent to manual review.

`npm run test:account-deletion` passes 14 isolated Node integration cases using the real installed SDK and a separate CLI process. Coverage includes OFF/missing configuration with zero requests, claim/checkpoint rejection, checkpoint ordering, exactly one hard-delete request, skips and mixed counters, explicit refusal, socket loss, infrastructure failure, malformed success JSON, the actual 20-second stalled-body deadline, and review-write failure stopping later batch work. Console secrecy is checked in every case. These mocks do not prove real Auth cascades, stale-token denial or Supabase Storage integration.

The Owner queue requires Owner role and recent TOTP and exposes only username, request time, and a fixed reason code. It does not provide a resolve/delete action. The user-facing account page explains that deletion is paused and files remain unchanged.

## Remaining gates

- Keep every request/cleanup gate OFF until the user accepts the UI and migration behavior is verified using a disposable local database with synthetic users and files.
- Before any Staging run, the user must separately authorize connecting the isolated Staging environment. Production is not authorized by this policy.
- A future audited Owner resolution action must define what happens to retained evidence and any linked published content. Do not infer erasure, transfer, or a retention period from the manual review state.
- Counsel review remains necessary for the applicable data-retention policy; this document records engineering behavior, not legal advice.
