# Phase 3 migration rollback guide

This is a local planning guide for Phase 3 migrations dated `20260930`, subsequent `20261001` forward corrections, the `20261003` Clarification V1 migrations, `20261004` Phase 3 migrations and forward fixes, and `20261005` updates. The later sets include cross-phase analytics/Hot work and the cross-phase PL/pgSQL lock-target cleanup; this is not a claim that every listed file belongs exclusively to Phase 3. None of these migrations has been applied to Staging or Production from this worktree. It is not an executable down-migration and does not authorize database changes.

## Rules before any rollback

1. Confirm the exact environment, migration ledger, applied migration sequence, active feature flags, scheduled jobs, API consumers, and any deployment-specific hooks. Never infer the applied state from this repository alone.
2. Use a verified environment-specific backup or snapshot before touching schema or data. If a backup cannot be verified, prefer a forward fix and keep the affected feature disabled.
3. Disable the relevant Next.js and database feature flags first. Stop workers and schedulers before changing scanner, evidence-access, notification, or email objects.
4. Prefer a new corrective migration. Do not edit or delete an already-applied migration, run a later migration's rollback in isolation, or restore an earlier function body without checking every dependent migration.
5. Preserve append-only audit rows, moderation decisions, revision snapshots, queued delivery evidence, and any data that cannot be reconstructed. A rollback that drops such data is not acceptable without an explicitly authorized restore plan.
6. If a rollback is necessary, operate on an isolated Staging project with synthetic data and record the before/after migration IDs, verified snapshot, commands, outcomes, and remaining drift. Do not use Production as a rollback rehearsal.
